# F04 — Conversation to SolutionBrief

Status: complete. Owner: coding agent (self-review). Depends on F02 (complete).

## What was built

- `alpha_contracts.briefs.SolutionBrief` (contract 0.2 §2): all top-level fields required,
  closed enums for delivery and surfaces, assumptions carry provenance
  (`model_default` / `user_answer` / `user_correction` + turn reference), open questions with
  options and "why it matters", `unavailable_capabilities`, `supersedes_revision` lineage.
- `alpha.capabilities.catalog`: the live CapabilityCatalog (compute available; records,
  artifacts, models, custom_ui, files, http, browser, messaging, schedules, audio unavailable
  with reason and arriving ticket). Rendered into the assistant's system prompt and served at
  `GET /api/capabilities`.
- `alpha.models.structured.StructuredInference`: non-agentic structured calls on the
  `claude-code-cli` route (`--json-schema`, no tools, settings ignored, no MCP, no session
  persistence) with usage rows; the `fake` route answers deterministically for control tests.
- `alpha.assistant`: turn schema (`AssistantTurnOutput`: delivery, interpretation, reply,
  ≤3 questions, assumptions, brief draft), prompts (rules from UX spec §3 + catalog),
  `AssistantService` (conversations, turns, brief revisions in SQLite; thinking →
  waiting_for_user / briefed / answered / failed; corrections and answers create new brief
  revisions; `answer` delivery creates no brief; no App/Task/build record is ever created by a
  brief).
- API: `POST/GET /api/conversations`, `POST /api/conversations/{id}/messages` (text, answers,
  use_defaults), `GET /api/conversations/{id}/briefs/{revision}`, `GET /api/capabilities`.
- Shell: the Assistant is now the front door (goal input with three illustrative prompts,
  "How Alpha understood it", assistant reply, questions with options plus "Something else",
  "Use these defaults for now", plain-language brief card with assumption tags "default" /
  "you chose" / "you corrected", "Change or add something", "Start over"). The synthetic
  runtime fixture moved behind a "Runtime fixture" toggle; Results renamed Activity.
- `just qualify-assistant` (opt-in live run over three request families) and
  `just verify-ticket F04`.

## Design notes

- The model never sees a credential; the shell never sees the model. Core owns brief identity
  and revision numbers; the model only proposes content.
- Delivery is decided by the nature of the goal, never by what is available today: a recurring
  background workflow is an App without custom UI (Prototype_Scope_and_Acceptance §1), so the
  WhatsApp weather request is briefed as an App whose missing capabilities are named. The first
  prompt and the first qualification verdict got this wrong (see F04.C01 findings).
- Latency: live turns measured 58–81 s on the CLI's default model (F04.C01), recorded for the
  M1 review; a faster model per route is a configuration choice, not a code change. The
  structured call is bounded at 300 s and the outputs are capped for brevity (5 journey steps,
  3 data needs, 5 actions, 3 acceptance examples, 6 assumptions, reply ≤120 words).
- The `fake` route keeps agreed answers and adds the change on a free-text correction so the
  rendered correction path is observable without the live model (F04.C03).
