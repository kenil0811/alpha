# F08 — Deliver, use and reopen a generated solution

Status: complete; stopped at M1 for review (docs/development/M1-review.md). Owner: coding agent
(self-review). Depends on F04–F07 (complete). Platform frozen for G1 at f7dada6.

## What was built

- **Creation** (`solutions/creation.py`, `api/creation_routes.py`). This is the loop from
  request to use: request → clarification → acceptance plan → live build → checks →
  activation.
  - One Core-owned record per brief revision, with stages in the person's words.
  - Stop, and failures with a next step (retry or revise).
  - An unfinished creation is marked failed after a restart and is never revived.
- **Acceptance planning** (`solutions/planner.py`). One structured model call turns the brief
  into the `ValidationPlan` before the build. The plan includes the screen's visible labels, and
  must pass consistency checks before anything is built. The fake route (control only) converts
  the brief's examples.
- **Identity.** The platform assigns `app_id` and the builder must keep it. The verifier's
  `package.identity` check proves it, both ways.
- **Registry** (`solutions/registry.py`, moved from `data/apps.py`). Activation is
  compare-and-swap on the current release. Each release records its origin, build, verification
  report, previous release and creation. `POST /api/builds/{id}/activate` accepts
  `expected_release_id`.
- **Screens.** The native host serves `alpha-ui://<app>/<version>/index.html` from the sealed
  Version with its own CSP, and checks the ids and the index. The shell frames the screen as
  scripts-only and answers its bridge with the App's declared grant.
- **Shell.**
  - Navigation: Assistant, My workflows and Activity.
  - The creation card, whose sample-data preview is labelled as such.
  - The workspace: the App's own screen, or, for an App without one, an actions view built from
    its input schemas, plus saved records with estimates marked.
  - The development fixture toggles appear only with `?dev` in a development build.
- **Environment.**
  - The host passes platform resources, the pinned Node and the headless browser to Core.
  - Core holds `caffeinate` while builds run.
  - The catalog lists records, artifacts, models and custom UI as available, with their
    operations and the profile versions.
- **Tests.**
  - `tests/integration/test_creations.py` has 6 tests: creation, no-screen use, reopen after
    restart, identity refusal, compare-and-swap, and two created Apps sharing a profile with
    cancellation.
  - `services/core/tests/test_cli_schema.py` checks schemas sent over the CLI route.
  - Shell tests cover the creation card, workflows, actions view, schema forms, navigation, the
    app bridge and run outcomes.
- **G1 tooling.**
  - `evals/g1.py` has `create`, `use`, `reopen` and `share`. It starts Core the way the host
    does.
  - `evals/g1_screen.mjs` drives an App's sealed screen with the shell's bridge host against
    the real Core.

## Found by G1 (fixed, failed attempts kept)

- **Attempt 1, calorie.** Stopped at "Deciding how to check it". The plan schema carried
  Pydantic's `discriminator`, and the Claude CLI's strict schema check refused the call before
  the model ran. The fake route sends no schema, so no offline test could see it.
  - Fix: `cli_schema()` sends only standard keywords (commit f2cb237).
  - Regression test: `test_cli_schema.py`.
  - Verified with one live planner call on the same brief (65 s, 4 scenarios and a screen plan).
  - Platform code was re-frozen, and G1 restarted from the first request.
- **Attempt 2, calorie.** The request was briefed after 179 s: the assistant asked two
  questions, and the defaults were accepted. The plan was written in 74 s. The live builder
  then used the whole 12-minute attempt and was stopped before it wrote the screen. Its output
  was about 50 KB of Python (a 21 KB `handlers.py`), generated at roughly a third of the F07
  speed, and the brief had grown extras such as "usual foods". The build ended after one attempt
  with 18 of its 30 minutes unused, because a timeout was terminal. The fixes use the bundle's
  levers (harness, brief quality) and keep its limits (2 repairs, 12 and 30 minutes):
  - **Harness:** a timed-out attempt is now checked as it stands and continued by the next
    attempt, whose REPAIR.md says that time ran out. It can never become ready by itself.
  - **Builder:** it is told its time and asked for the smallest code that passes, Python first,
    then the screen. It also keeps the assigned `app_id`; its old rule still said to choose one.
  - **Assistant:** the first version keeps to the main journey, and extras become assumptions
    for later.
- **Attempt 3, calorie.** With the smaller brief, the builder finished within its attempt
  (10 min) and wrote the screen. Every behaviour check still failed, because the planner wrote
  the output expectation `{"id": "*", "revision": "*"}` meaning "any value", and the matcher
  compared `"*"` literally. The candidate had returned a real id and revision. No honest repair
  could pass, and one that returned `"*"` as an id would have been gaming the check, so the run
  was stopped at the start of its first repair.
  - Fix: `{"$any": true}` is now the documented any-value marker in the planner prompt, the
    matcher and PLAN.md. A literal `"*"` in expected outputs or stored values (never inputs) is
    read as that marker.
  - Unit tests reproduce the G1 case.

## G1 result (frozen f7dada6)

All three requests went through live generation and primary use, and none of the generated
source was edited:
- **Daily Food Log.** Own screen; 1 attempt; 15.0 min from request to ready.
- **Job Opening Tracker.** Own screen; 2 attempts, because the type check caught a screen bug
  and the repair fixed it; 15.9 min.
- **Held-out Fits In Today Planner.** No custom screen; 1 attempt; 6.5 min.

The three share one runtime profile. A run cancelled in one App left the other untouched, and
all three reopened with the same Versions and data. Estimated generation cost was $6.81 on the
subscription route. Details: docs/development/evidence/F08.C01–C04.md and
logs/G1-20260926/.

What remains open is listed in M1-review.md:
- the native-window view of generated screens, which I have not seen myself;
- time to value above the 5-minute target;
- refusal wording that shows a Python class name;
- required fields that don't block empty submissions;
- the kit chart's oversized rendering with one day of data;
- progress counters that add up across attempts.
