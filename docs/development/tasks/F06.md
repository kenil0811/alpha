# F06 — Reusable interaction kit

Status: complete. Owner: coding agent (self-review). Depends on F03, F04 (complete).

## What was built

- **`packages/ui-kit` (`@alpha/ui-kit` 0.1.0)**: tokens (`styles/tokens.css`, light and dark,
  contrast-tested) and kit styles. The components are:
  - layout: `Page`, `Section`, `Stack`, `Cluster`, `Columns`
  - controls: `Button`, `Field` and the text/number/date/select/textarea/checkbox fields, `Form`
  - patterns: `QuickEntry`, `FilterBar`, `RecordTable` with `Pager`, `DetailDrawer` with
    `DetailList`, `ReviewQueue`, `MetricCard`, `TrendChart` with `RangeSelect`
  - feedback: `StatusMessage`, `Badge`, `EmptyState`, `LoadingState`, `ErrorState`,
    `OperationStatus`, `ProvenanceNote`

  Bridge-backed data comes through `AlphaApp`/`AlphaProvider`, `useView`, `useAggregate` and
  `useAction`, which settles only on the platform's outcome and refreshes views after a success.
  Typed filter builders and formatting helpers are included. `@alpha/ui-kit/testing` provides an
  in-memory App behind the real bridge protocol. `REFERENCE.md` is the builder-facing reference,
  shipped in the packed package. `reference/` holds a development reference sheet with every
  pattern in populated, empty, loading and failing states and a long-label mode (`just kit-reference`).
- **Bridge (`packages/ui-bridge`)**: `records.query` now carries a typed filter, sort, limit and
  cursor, validated at the host. The package builds to JavaScript for packing.
- **Core**: `app.yaml` `ui` declaration of read views and UI-callable actions (contract
  `UiDeclaration`/`ViewSpec`), validated against collections and actions. Core enforces views on
  `POST /api/apps/{id}/views/{view}/query`. App detail exposes the declaration. Profile
  verification covers `ui_build` profiles.
- **UI build profile** (`tools/build_ui_profile.py`, run by `just bundle-core`) and the trusted
  build tool (`tools/ui_build/build_app_ui.mjs`), with provenance and a closed CSP.
- **Two neutral compositions** (`tests/ui/compositions/review`, `…/entry`) and an App template
  (`templates/app`). The compositions run against the neutral `entries-fixture` App
  (`tests/fixtures/apps/entries_app`).
- **Shell**: `apps/desktop/src/apps/appBridge.ts` derives a session from an App's UI declaration
  and answers bridge requests with Core, for reuse in F08. The Core client reads structured
  errors. `kit-fixture.html` is a development-only qualification page hosting both compositions.

Decisions: docs/development/decisions/2026-09-25-f06-interaction-kit-and-ui-build-profile.md.

## Findings during the checks (all fixed)

- Frames sandboxed without `allow-forms` never fire `submit`: the first build saved nothing.
  The kit's `Form` now submits itself, and a test reproduces the sandbox.
- At 768 px a long table heading forced sideways scrolling; headings now wrap.
- A loading trend looked like "no entry" every day; a loading state is shown instead.
- Failure messages lacked a full stop and a count read "1 entries".
- One intermittent failure of the bulk-review test was seen and could not be reproduced in 26
  later runs; a diagnostic prints the page state if it recurs.

## Scope boundary kept

No mandatory UI DSL. Generated code writes React and composes the kit; tables are one option. No
generic CRUD-only bar: quick entry, review and trend patterns are first-class. No founder-written
example App: the compositions are neutral and exercise patterns. No remote runtime imports and no
per-App Node server.
