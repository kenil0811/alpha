# F05.C02 — Wrong-owner operations, invalid values and unsafe/unbounded queries fail

- Check: F05.C02 (evidence kind: integration)
- Code: commit df1b554
- Environment: macOS 26.6.2 (25G83) arm64; CPython 3.13.9; real Core process (dev environment) with real SQLite; App workers on the published runtime profile pyprof-48e953297d79b3ac3547 (uv 0.12.17 staged install of alpha-sdk 0.1.0 and alpha-app-worker 0.1.0 on the uv-managed cpython-3.13.9-macos-aarch64-none); model route `fake` unless stated
- Command: `just verify-ticket F05` → exit 0 (log: docs/development/evidence/logs/F05-verify-ticket-df1b554.log); plus in-process broker tests in services/core/tests/test_f05_data_and_broker.py (real SQLite).
- Reviewer: self-review (coding agent)

## Expected
Anything outside an App's own records, declared schema, declared capabilities and platform query limits fails with a typed reason, and a failed operation leaves stored data unchanged. Workers cannot name an owner, forge or borrow authority, or smuggle SQL.

## Observed (tests/integration/test_app_rejections.py, 28 tests; each case runs inside a real App worker)
| Case | Result |
|---|---|
| Extra `app_id` field in a raw query call | invalid_input |
| Filter given as an SQL string; SQL text as a field name | invalid_input |
| Page of 5,000 records | limit_exceeded (maximum 1,000; cursor required) |
| Filter nested 7 levels; 40 conditions | limit_exceeded |
| Cursor reused with a different query | invalid_input |
| Unknown operation `records.drop_all` | invalid_input |
| Unknown collection; filter on an undeclared field | not_found; invalid_input |
| Bad choice, missing required field, text for a number, negative quantity, undeclared field, naive datetime, 201-character title, 600-byte JSON | invalid_input |
| Reference to a record that does not exist | invalid_input |
| Idempotency key reused with different values | conflict |
| Made-up workload token on the worker's own pipe | unauthenticated |
| Update or delete at a stale revision | conflict ("expected revision 1, current 2"); the delete ends the run failed |
| Duplicate unique `code`; deleting an item that notes still reference | conflict |

Store unchanged after every rejected case (record count compared before and after).
- Batch of three creates whose third value is invalid: the run failed with "operation 3 of 3", and none of the three records exists.
- Wrong owner: the tally App reading the items App's record id → not_found; reading its artifact id → not_found; the tally App calling `models`, which it did not declare → forbidden. Both Apps have a collection named `items`; each lists only its own rows, and each store file is stamped with its owner.
- Tokens: a run stored its own token in a record; a later run presented it on its own pipe → unauthenticated. In-process, each of two live runs' tokens was refused on the other run's pipe ("belongs to a different run"). Tokens were refused after revocation and after a simulated Core restart. Only SHA-256 hashes are stored, and all tokens were revoked when their runs ended.
- Invocation: a wrong input type → 422 before any run exists; unknown action and unknown App → 404; an origin the action does not allow → 403. The run count was unchanged.
- Results: a result violating the declared output schema → failed `output_schema_violation`. A handler printing 4,000 forged protocol lines and 200 KB of stderr still produced exactly its real result.
- The trusted shell's query route enforces the same limits: 422 for 5,000 records, for an SQL-text field name and for an unknown top-level `sql` key.

## Limitations
Functional checks against a cooperative OS: F20 qualifies containment of a hostile worker, for example reading another App's files directly. Wrong-owner access is refused by store selection from the authenticated run, not by OS permissions on the store files.
