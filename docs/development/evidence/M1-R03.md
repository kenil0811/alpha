## F13: Stop and switching on are decided atomically

`solutions/creation.py` now makes every state change conditional. The control store serialises
transactions (one connection, a lock, `BEGIN IMMEDIATE`), so Stop and switching on cannot
interleave:
- **Stop** (`cancel`) reads the state and writes `cancelled` in one transaction. It refuses once
  switching on has begun ("it is already being switched on and can no longer be stopped") and
  after completion ("the creation is already active").
- **After build submission**, the creation moves to `building` only if it is still live. If Stop
  won meanwhile, the build it just submitted is cancelled.
- **Switching on** starts with `_claim_activation`, a conditional move to `activating`. An
  accepted Stop always wins this claim, so no release is made.
- **The shell** hides Stop while switching on ("Switching it on now; this can no longer be
  stopped.") and shows Core's refusal if a Stop arrives too late.

**Tests**
- `services/core/tests/test_creation_cancel.py` runs the real `CreationService` on real SQLite,
  with controlled builds, planner and assistant. It enters each window on purpose:
  - Stop during build submission: the creation is cancelled, the new build is cancelled, and
    nothing is activated.
  - Stop after the build is read as ready but before switching on: cancelled, with no activation.
    This is the review's probe R07 window.
  - Stop after switching on was claimed: refused with the true reason, and the creation ends
    active.
  - Stop after completion: refused.

  **The first three fail on the pre-repair code** and pass now.
- `tests/integration/test_creations.py` runs on the real stack. Core's creation check interval is
  set to 8 s (`ALPHA_CREATION_POLL_SECONDS`), which opens the window between "build ready" and
  switching on:
  - Stop accepted in that window leaves the creation `cancelled` with no release, no App and no
    `build.activated` event, 10 s later.
  - Stop after completion returns 409, and the creation and App stay active.
- `workflows.test.tsx`: no Stop while switching on, and a late Stop shows Core's reason.

## F10: an open screen keeps working past its session lifetime

- **Bridge host** (`@alpha/ui-bridge`, `host.ts`): a request that arrives after expiry is held.
  The trusted caller's `renew` decides whether to extend the session or end it. The request then
  runs **once**, or not at all; it is never replayed. If the check itself fails, for example
  because Core is unreachable, the session is kept and the person is asked to try again. Without
  a renewer the old behaviour, revocation, applies.
- **Shell** (`appSessionRenewer`): renews only if the App's current release is still the
  session's release and the declared views and UI actions are unchanged. Otherwise it ends the
  session with `release_changed` or `grant_changed`, and the workspace says: "This workflow was
  updated while its screen was open. Reopen it to continue; what you typed is still on the
  screen."

**Tests**
- `packages/ui-bridge/src/bridge.test.ts`:
  - after expiry, a request succeeds once with a single renewal and the session stays open;
  - a changed release ends the session, and the request is not executed;
  - a failed check keeps the session, and the next request succeeds.
- `apps/desktop/src/apps/appBridge.test.ts`: the renewer extends an unchanged session, ends it
  on a changed release or grant, and lets a failed check surface.
