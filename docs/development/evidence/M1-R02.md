## F04: a failed model estimate cannot become a saved number

The fix is in the platform, not in the retained calorie package, which stays as it was.
- **Plan steps can make the model fail.** `InvokeStep.model` in contract 0.2 is an optional field
  with values `normal`, `unavailable`, `malformed` and `timeout`. A preview's model service
  (`builds/preview.py`, `FaultableModels`) then fails exactly as a real failure reaches an App.
  The planner is told to add such a step for every action that fills a value from a model, and
  to accept only a refusal with nothing stored, or the value left unknown.
- **The verifier checks every model action by itself.** `builds/plan.py`,
  `run_model_failures`, produces a required check `model.failure.<action>`. For every action
  that requires `models`:
  1. it finds a planned step where the action really calls the model;
  2. it learns from provenance which stored fields hold the estimate;
  3. it runs that step again with the model unavailable, malformed and timed out.

  The check fails if:
  - a number is saved in an estimate field;
  - a failed run still changed data;
  - a model result is stored without an estimate label.
- **Unknown means absent or empty.** An expected `null` in a plan matches a value that is absent
  or null. A stored `0` is a value, not unknown (unit test).
- **Guidance.** The builder's rules, the SDK reference and the App contract now say: never
  substitute a guess; store `None` or refuse; label estimates with `estimated=`.

**Tests** (`tests/integration/test_model_failure.py`: real Core, profiles and render check; fake
builder and fake App model route):

| Variant | Result |
|---|---|
| `estimate_honest`: stores the time as unknown when the model fails | **ready**. `model.failure.add_timed_note` passed and found the estimate field `notes.minutes`. The planned `"model": "unavailable"` scenario passed. |
| `estimate_invented`: saves 30 when the model fails, the G1 calorie defect | **failed**: "model unavailable / malformed / timeout: add_timed_note saved minutes=30 … although no estimate was available" |
| the same, with the planned failure scenario | **failed** at `behavior.timed_offline.unknown` |
| `estimate_unlabelled`: stores the model's number as if typed | **failed**: "stored a model result without labelling it an estimate" |

## F08: unknown days are not zero

Generated code decides the metric, so the repair works through generation and evaluation, not
through a domain branch in Core:
- **The App contract** says: "Unknown is not zero … An average over days counts only the days
  with entries and says how many there were ("1,060 per logged day · 1 of 7 days logged"). A
  value the person enters as 0 is a real zero."
- **The builder rules** say the same.
- **The planner** must add a scenario with a gap, and assert the per-period average and the
  coverage exactly, with no wildcards for computed values.

The G1 run in M1-R07 checks the calorie tracker natively against the review's exact rule: one day
of 1,060 in a 7-day view shows 1,060 per logged day and 1 of 7, and with no logged days the
average is unknown. The shared chart's coverage display belongs to M1-R05.

## F11: data-location statements come from configuration

- `models/disclosure.py` states, from the configured routes, what is stored on this Mac and what
  is sent to "Anthropic's Claude service over the internet" (the `claude-code-cli` route).
- The assistant's system prompt carries these DATA FACTS and forbids "nothing leaves this Mac".
- Each turn's output is grounded before it is stored. An unqualified locality claim, such as
  "Everything stays on this Mac; nothing is sent anywhere", is replaced by the grounded statement
  on remote routes, and the turn records what was replaced (`grounded`). The unit tests use the
  exact sentences the live assistant produced in G1, and check that true statements like "Your
  records are stored on this Mac." are left alone.
- Conversations carry `data_notice`, shown under the brief as "Where your data goes: …". An App's
  detail carries `data_notice`, shown in its workspace; for an App that uses estimates it names
  what is sent and where.
