## The G1 verdict false positive

`evals/g1.py` passed any journey call marked `expect: failed`, whatever happened. That included
one that succeeded and wrote data (review probe R06).

Each call is now judged by `call_verdict`, with the App's records read before and after it:
- An expected refusal must end **failed**, or be refused before running.
- It must say the reason when the journey gives `expect_message`.
- It must leave stored data unchanged.
- An expected success must succeed.

Four tests cover these, including the review's exact case: an expected refusal that succeeded
and wrote. Found alongside it: `reopen` read `reopen_action` from the wrong place, so the
"use again after reopening" step never ran. Fixed.

## The verifier's own refusals

The same gap existed inside the platform verifier. An `expect: failed` step passed if the run
failed, even when the handler had already saved something. It was caught only if the plan
happened to read the collection back afterwards.

A failed step that changed any collection now fails: "add_note failed as expected but changed
stored data in notes".

New fixture variant `refusal_writes`: a handler that saves a blank note, then raises. The test
uses a plan with no records step after the refusal. **On the pre-repair verifier this candidate
was made ready**; now the build fails on that check.

## Every material brief outcome has an assertion

The acceptance planner now checks a model-written plan against the brief
(`coverage_problems`). An incomplete plan is sent back once with the exact gaps named. If it is
still incomplete, planning fails plainly ("the checks are incomplete: …"), rather than building
against checks that prove nothing.

The plan must:
- run every brief action successfully;
- assert at least one fixed value for each action that only computes (wildcards alone don't
  count; model-written results are exempt);
- run each model-using action with the model unavailable;
- read back every collection the App keeps.

The planner's instructions say the same. Three unit tests cover this. On the old planner the
coverage check does not exist, and an incomplete plan was accepted as final.

## An actual shell journey

`tests/integration/test_shell_journey.py` drives the **real shell build** in the pinned headless
browser against a real Core with the control routes. It proves the shell and platform path, not
generation quality. The probe adds the control builder's package hint to the one "Create it"
request; nothing else is altered. Observed in the run kept in
`docs/development/evidence/captures/M1-R06/` (result and three screenshots):

| Step | What the person sees |
|---|---|
| Ask, Create it | "Notes (fixture) is ready. It passed all 10 of its checks." |
| Open | The main action "Add a note" leads |
| Save "Call the bank" | "Done."; Saved shows one note dated today |
| 301-character title | "Not done. notes.title is longer than 300 characters"; what was typed is kept; nothing saved |
| More actions → Count notes | "Done. Count 1" |
| Reload, My workflows, Open | Same App and name; the one note is still there |
| Activity | Add note (done), Add note (failed, "Not done: …"), Count notes (done) |

The test also confirms through Core that exactly one note is stored. No page or console errors.

**Found by the journey and fixed:** the ready card named the App by its *planned* name ("Notes
list"), while My workflows used the App's real name. The card and the "after it was made" notice
now use the made App's name. The new shell test fails on the old card.

**Found, not changed here:** the store's refusal wording names the field by path
("notes.title …"). It is understandable but not ideal. Builders rely on this wording, and every
App shares it, so it is left for the product call and will be looked at in the native session.

## `g1.py record`: evidence from a session in the Alpha window

`python evals/g1.py --g1-dir <dir> record --label <name> --conversation <id>` runs after Alpha
is quit, on the same data directory. It opens the stores read-only and writes
`record/<name>/native.json`, containing:
- the conversation, its turns and briefs;
- creations with their plans, history and failure;
- builds, attempts and build events;
- the App, its versions and releases;
- its runs and every stored record;
- model usage for each step, with a cost estimate.

It also copies each attempt's report, package and screenshots. An integration test runs it on a
real created App: the output is complete, and **`control.sqlite` is byte-identical afterwards**.
