# Roadmap and scope

Baseline R2 · 24 September 2026. Product intent is in Product Vision; exact tickets/gates are in Prototype_Scope_and_Acceptance.md. This roadmap does not establish additional phase numbering.

## Now: prove useful user-driven creation

M0 qualifies the essential dependencies. M1 must produce usable results from ordinary requests through a real builder and shared design kit. M2 makes those results safe to change and recover. M3 reaches external systems and supported application forms. M4 adds recurrence, repair and measured breadth. M5 qualifies installation, protection and usability for a private Mac alpha. All are pending implementation.

The first engagement covers F01–F08 only and stops at the M1/G1 product review. Later milestones are planned but inactive until explicitly authorized; dependency readiness alone does not authorize them. The first product gate is G1. Do not delay user-visible generation behind a complete capability catalogue, a workflow editor or multiple mandatory harness implementations. Browser/form and no-dashboard workflows are planned alpha outcomes, not optional aspirations after building two personal apps.

## Next: expand based on observed work

| Track | Trigger for investment | Deliverable and exit condition |
|---|---|---|
| Service capabilities | Repeated user workflows blocked by missing access or unreliable browser paths | Shared connector/provider with declared inputs, effects, grants, receipts and tests; new workflows can compose it |
| Audio/document processing | Users need portal/study material transformed into durable media | Qualified parsing and synthesis, provenance, usable output files and bounded cost; no claim based on a text transcript alone |
| Always available | Users lose value because their Mac sleeps or is offline | Explicit per-App cloud deployment, authenticated remote access, isolated workers, durable scheduler, tenant state/secrets and usage controls |
| Windows | Demand justifies a second supported host | Native IPC, credentials, process/containment, browser packaging, install/update and lifecycle gates on Windows |
| User context/memory | Users repeatedly supply the same selected facts/preferences | Inspectable local claims with provenance, correction, revocation and explicit cross-App scope |
| Desktop actions | Important work cannot be handled by APIs/browser/files | Qualified OS adapter and visible scoped authority; observation alone never authorizes action |
| Voice/screen input | Measured input friction warrants it | Explicit capture, meaningful consent/status, bounded retention and extraction feeding the same assistant |

Cloud is a required eventual direction, not part of the first private release. Preserve provider seams now; do not build cloud queues or synchronization ahead of evidence. Windows portability means shared business logic and explicit OS adapters, not a false claim that a cross-platform framework alone completes support.

## Deliberately later

Active-active local/cloud sync, anonymous public hosting, team/enterprise administration, marketplace, billing, mobile execution, continuous ambient monitoring, universal desktop control and autonomous high-impact actions. None is required to prove the core product.

## Scope change test

Ask: does the change improve the generic creation/use/repair loop; does an existing shared capability suffice; what new authority or maintenance burden does it introduce; which gate will prove it? A request for one example workflow is not permission to hardcode that domain into Core. A genuinely new provider should be justified by reusable value and tested independently.
